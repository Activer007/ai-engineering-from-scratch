# ReWOO 与 Plan-and-Execute：解耦规划

> ReAct 在同一个流程中交错进行思考与行动。ReWOO 则将二者分开：先制定完整计划，再执行。token（词元）用量缩减为原来的五分之一（5x），HotpotQA 准确率提升 +4%，而且还能把规划器蒸馏成一个 7B 模型。Plan-and-Execute（规划后执行）将这种方法推广为一种模式；Plan-and-Act 则将这种规划与行动分离的模式扩展到了网页导航。

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** 阶段 14 · 01（智能体循环）
**Time:** ~60 分钟

## 学习目标

- 解释为什么 ReWOO 的规划器（Planner）/ 工作单元（Worker）/ 求解器（Solver）分工，相比 ReAct 的交错循环能够节省 token 并提高稳健性。
- 仅用标准库实现表示计划的有向无环图（DAG）、按依赖顺序运行的执行器，以及合成工作单元输出的求解器。
- 根据 2026 年的“五种工作流模式”框架（Anthropic），判断任务何时应先规划再执行，何时应采用交错进行的 ReAct。
- 识别长时程网页或移动端任务何时需要 Plan-and-Act 的合成计划数据。

## 要解决的问题

ReAct 将思考、行动、观测交错进行的循环简单而灵活，但每次工具调用都必须携带此前的完整上下文，包括之前的每一次思考。token 用量随步骤深度呈二次增长。更糟的是，一旦工具在循环中途出错，模型就必须根据错误观测重新推导整个计划。

ReWOO（Xu 等，arXiv:2305.18323，2023 年五月）注意到了这一点，并选择了另一条路：预先规划整个任务，并行获取证据，最后合成答案。调用一次大语言模型（LLM）来规划，调用 N 次工具来获取证据（可以并行），再调用一次 LLM 来求解。代价是灵活性较低（计划是静态的），换来的是显著提高的 token 使用效率，以及更清晰的故障模式。

## 核心概念

### 三种角色

```text
Planner:  user_question -> [plan_dag]
Workers:  [plan_dag]     -> [evidence]        (tool calls, possibly parallel)
Solver:   user_question, plan_dag, evidence -> final_answer
```

规划器生成一个 DAG。每个节点指定工具、参数，以及它依赖哪些先前节点（通过 `#E1`、`#E2` 这样的引用表示）。工作单元按拓扑顺序执行节点，求解器则将所有结果整合起来。

### 为何能将 token 用量缩减为原来的五分之一（5x）

ReAct 的提示词（prompt）长度随步骤数线性增长。到了第 10 步，提示词中包含思考 1、行动 1、观测 1，再加上思考 2、行动 2、观测 2，依此类推。每个中间步骤还会重复包含最初的提示词。

ReWOO 的开销来自一个较大的规划器提示词、N 个较小的工作单元提示词（每个只包含工具调用，没有完整的思考链），以及一个求解器提示词。论文在 HotpotQA 上测得，token 用量缩减为原来的约五分之一（~5x），同时准确率的绝对提升为 +4。

### 为什么更稳健

如果 ReAct 中的工作单元 3 出错，循环就必须在运行中途通过推理摆脱错误。在 ReWOO 中，工作单元 3 返回一个错误字符串；求解器在原始计划的上下文中看到这个错误，可以平稳降级。故障定位以节点为单位，而不是以循环步骤为单位。

### 规划器蒸馏

论文的第二个结果是：由于规划器不读取观测，可以用 175B 教师模型的规划器输出对一个 7B 模型进行微调（fine-tuning）。小模型负责规划，推理时不再需要大模型。这如今已经成为常见做法：许多 2026 年的生产环境智能体（agent）采用小规划器搭配大执行器，或者反过来。

### Plan-and-Execute（2023）

LangChain 团队在 2023 年八月的文章中将 ReWOO 推广为一种模式，命名为 Plan-and-Execute。规划器预先输出步骤列表，执行器逐步执行；还可以添加一个重新规划器，在观测结果后修订计划。它比 ReWOO 更接近 ReAct（重新规划器把观测重新引入规划），但仍保留了节省 token 的优势。

### Plan-and-Act（Erdogan 等，arXiv:2503.09572，ICML 2025）

Plan-and-Act 将这种模式扩展到长时程网页和移动端智能体。其关键贡献是合成计划数据：带标注的轨迹生成器产出明确包含计划的训练数据。这些数据用于微调规划器模型，使其在 WebArena 一类任务中经过 30–50 步之后仍能持续工作；而在这些任务上，单条 ReAct 轨迹会失去连贯性。

### 何时选择哪种模式

| 模式 | 适用情形 |
|---------|------|
| ReAct | 任务较短、环境未知，需要根据变化处理异常 |
| ReWOO | 结构化任务，工具已知，对 token 用量敏感，证据可并行获取 |
| Plan-and-Execute | 类似 ReWOO，但在部分执行后重新规划 |
| Plan-and-Act | 长时程任务（>30 步），涉及网页、移动端或计算机操作 |
| 思维树（Tree of Thoughts） | 值得为搜索付出成本（第 04 课） |

Anthropic 在 2024 年十二月给出的建议是：从最简单的方案开始。如果任务只需要调用一次工具再做个总结，就不要构建 ReWOO。如果任务是一项需要 40 步的研究工作，就不要仅靠 ReAct。

## 动手实现

`code/main.py` 实现了一个教学用 ReWOO：

- `Planner`：通过脚本化策略，根据提示词生成计划 DAG。
- `Worker`：通过工具注册表（tool registry）分派每个节点的工具调用。
- `Solver`：通过脚本化的组合逻辑，读取证据并生成最终答案。
- 依赖解析：将 `#E1` 这样的引用替换为先前工作单元的输出。

演示回答的问题是：“法国首都的人口是多少？请按 million（百万）为单位四舍五入。”它采用两步计划：(1) 查找首都，(2) 查找人口，然后求解。

运行方式：

```text
python3 code/main.py
```

运行轨迹先显示完整计划，再显示工作单元的结果，最后显示求解器合成的答案。将其 token 数量（这里打印的是粗略的字符数）与 ReAct 式交错运行比较，会发现 ReWOO 在这类结构化任务上更有优势。

## 实际使用

LangGraph 以实现范例的形式提供 Plan-and-Execute（ReAct 使用 `create_react_agent`，规划后执行使用自定义图）。CrewAI 的 Flows 直接表达了这一模式：先定义任务，再由 Flow DAG 执行。Plan-and-Act 的合成数据方法仍主要处于研究阶段；它的运行时模式（显式计划 DAG）则已经通过 LangGraph 和 CrewAI Flows 用于生产环境。

## 交付成果

`outputs/skill-rewoo-planner.md` 根据用户请求和给定的工具目录生成 ReWOO 计划 DAG。它在交给执行器之前校验计划：无环、每个引用都能解析、每个工具都存在。

## 练习

1. 让独立计划节点的工作单元并行执行。在包含 6 个节点、2 个并行组的 DAG 上，这会带来什么收益？
2. 添加一个重新规划器节点，只要有工作单元返回错误就触发。对 ReWOO 做怎样的最小改动，就能让它成为 Plan-and-Execute？
3. 用一个小模型（7B 级别）替换 `Planner`，并继续让前沿模型承担 `Solver` 的工作。比较端到端质量：这种分工会在哪些地方失效？
4. 阅读 ReWOO 论文第 4 节关于规划器蒸馏的内容。从概念上复现 175B -> 7B 的结果：需要哪些训练数据？如何评价计划质量？
5. 将这个教学示例改成 Plan-and-Act 的轨迹形式：计划是一段序列，而不是 DAG。取舍会发生什么变化？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------------|------------------------|
| ReWOO | “不依赖观测的推理” | 先规划，再并行获取证据，最后求解；规划提示词中没有观测 |
| Plan-and-Execute | “LangChain 的规划后执行模式” | 在 ReWOO 中加入可选的重新规划器节点，在执行后重新规划 |
| Plan-and-Act | “扩展后的规划后执行” | 显式分离规划器与执行器，并用合成计划训练数据支持长时程任务 |
| 证据引用 | “#E1, #E2, ...” | 计划节点中的占位符，在分派时替换为先前工作单元的输出 |
| 规划器蒸馏 | “小规划器，大执行器” | 用大型教师模型的规划轨迹微调小模型 |
| token 使用效率 | “更少的往返交互” | 论文中，ReWOO 在 HotpotQA 上的 token 用量相较 ReAct 缩减为原来的五分之一（5x） |
| DAG 执行器 | “拓扑分派器” | 按依赖顺序运行计划节点，同一层内并行执行 |
